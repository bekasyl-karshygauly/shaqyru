# Клиентские статусы и WhatsApp

Состояние 2026-10-28: код, форма и закрытая очередь готовы; миграция применена к проекту Supabase **shaqyru**. WhatsApp Cloud API у владельца ещё не подключён. Реальные сообщения клиентам не отправлялись, флаг автоматической отправки по умолчанию выключен. Приложение WhatsApp Business на телефоне не является подключением Cloud API.

## Что работает на сайте

- Организатор ставит статусы «Принята», «В обработке», «Обсуждение», «Нужны правки», «Готово к публикации», «Отклонена» и публикует приглашение прежней кнопкой.
- Отказ требует причины, которую видит клиент. Отклонённый заказ нельзя опубликовать или вернуть в работу подтверждением старой цены/добавлением правки. Повторная отправка заявки возвращает её на рассмотрение; история сохраняется.
- В заявке есть необязательное согласие получать статусы в WhatsApp на собственный номер. Оно выключено по умолчанию. При неподключённом канале форма честно показывает, что отправки пока нет; заявку можно отправить без подписки.
- Подписку можно отозвать, в том числе после публикации или при временно выключенном провайдере. Смена контактного номера без нового согласия выключает подписку.
- Ручная кнопка «Написать клиенту в WhatsApp» открывает подготовленный текст и текущий статус. Организатор сам нажимает «Отправить» в мессенджере. Это не автоматическая отправка.

## Серверная часть

`client-notifications.js` использует отдельную таблицу `shq_client_notifications`, не меняя очередь уведомлений организатору. Триггер атомарно создаёт событие при новом статусе или согласии; обычные правки текста и дизайна не рассылаются. Старые ожидающие статусы заменяются актуальным, отзыв согласия отменяет ожидающие события. Перед отправкой повторно проверяются номер, время/версия согласия, текущий статус и возраст события (до 7 дней).

Захват с SKIP LOCKED и lease защищает от одновременной обработки. Временные ошибки повторяются до 6 попыток. После неопределённого сетевого результата дубль всё же возможен; exactly-once не обещается. Работающий сервер проверяет очередь каждые 20 секунд и сразу после изменения заказа. На засыпающем бесплатном хостинге повторы могут ждать пробуждения процесса.

Ответ Meta с message ID означает только приём API, а не доставку/прочтение. Кабинет показывает это явно. Для подтверждения доставки нужен проверенный подписанный webhook Meta; его подключение и реальный тест входят в следующий этап настройки аккаунта.

Сообщения содержат номер заявки, название праздника, текущий статус/причину отказа. Только после публикации добавляется гостевая ссылка. Нет токена владельца, ссылки редактора или кабинета. Если доступ гостям закрыт, ссылка не предлагается к отправке.

RLS включён; anon/authenticated не имеют доступа к очереди или RPC, только серверный service_role. Миграция `20261028083345_client_status_notifications.sql` не подписывает старые контакты и не рассылает исторические заявки.

## Подключение Meta: следующий шаг с владельцем

1. Войти в [Meta for Developers](https://developers.facebook.com/apps/) и настроить WhatsApp в developer app. Начать с официального тестового номера и подтверждённого собственного получателя. Тестовые ресурсы не означают готовый канал для клиентов. Никакой регистрации или принятия условий за владельца не выполнялось.
2. Для рабочего номера выбрать официальный путь: отдельный номер для Cloud API либо сохранение приложения через поддерживаемый [Coexistence / Embedded Signup](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users). Не удалять текущий Business account и не перерегистрировать его вслепую. Coexistence может требовать провайдера/партнёра.
3. Утвердить utility-шаблон. Всегда отправляется template, чтобы обновления работали и вне 24-часового окна. Имя, локаль и категорию утверждает Meta.
4. В Render → Environment сохранить токен только сервером, phone-number ID, поддерживаемую версию Graph API и шаблон. Токен не пересылать в чат/GitHub/клиентский JS. Локальная `.env` сама не переносится в Render.
5. Проверить отправку на собственный подтверждённый тестовый номер, обработку ответа и webhook. Согласовать рабочий номер и расходы перед включением для клиентов. Реальной доставки пока не проверено.

Переменные (реальных значений в репозитории нет):

```dotenv
WHATSAPP_ACCESS_TOKEN=
WHATSAPP_PHONE_NUMBER_ID=
WHATSAPP_API_VERSION=
WHATSAPP_CLIENT_STATUS_TEMPLATE=
WHATSAPP_CLIENT_TEMPLATE_LANGUAGE=ru
WHATSAPP_CLIENT_NOTIFICATIONS_ENABLED=0
PUBLIC_URL=https://shaqyru-cysn.onrender.com
```

Имя шаблона, например `shaqyru_order_status`. Тело с четырьмя текстовыми переменными в фиксированном порядке:

«Шақыру. Обновление заявки {{1}} на приглашение «{{2}}»: {{3}} {{4}}».

1. ID заявки.
2. Название/имена.
3. Текущий статус и при необходимости причина отказа.
4. Следующий шаг; для опубликованного открытого приглашения — гостевая ссылка.

Пример и категорию должен одобрить Meta, одобрение не гарантируется. RU-тексты идут с утверждённой русской локалью; KZ-тексты поддержаны при отдельном одобренном шаблоне с соответствующей локалью. Имеющиеся шаблоны уведомлений организатору остаются отдельными.

Рабочая отправка может тарифицироваться Meta и/или выбранным провайдером. Не обещать бесплатные сообщения: текущие ставки и условия проверяются в WhatsApp Manager перед подключением billing. Источники: [Get started](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started), [opt-in](https://developers.facebook.com/documentation/business-messaging/whatsapp/getting-opt-in), [pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/non-template-messages).
