# Подключение аккаунтов и облачных черновиков

Код входа и хранения готов. Эта инструкция нужна для включения реальной услуги; тесты используют подменённый Supabase и не создают пользователей или письма.

1. В том же проекте Supabase выполните `migrations/003_accounts.sql` через SQL Editor. Таблица облачных черновиков закрыта для ролей `anon` и `authenticated`; доступ идёт через сервер после проверки пользователя. Существующие приглашения и оплаты миграция не меняет.
2. Добавьте `SUPABASE_ANON_KEY` — публичный publishable/anon ключ проекта — в `.env` или секреты хостинга. `SUPABASE_SERVICE_KEY` оставьте только на сервере. Не отправляйте сервисный ключ в чат или браузер.
3. Задайте `PUBLIC_URL=https://ваш-домен` без пути. Сервер использует его для проверки Origin. Для локального входа используйте отдельную конфигурацию с `PUBLIC_URL=http://localhost:3108` и тем же портом сервера.
4. В Supabase Auth включите email provider и настройте SMTP. В шаблоне **Magic Link** поместите одноразовый код `{{ .Token }}`. Интерфейс ожидает ввод кода, а не переход по ссылке. Проверьте также шаблон подтверждения регистрации, если настройки вашего проекта используют его для первого входа. Не отключайте подтверждение email ради теста.
5. Запустите приложение с окружением: `node --env-file=.env server.js`. Для рабочего HTTPS сайта настройте прокси и `TRUST_PROXY_HOPS` по фактической схеме размещения. Cookies сессии имеют HttpOnly и SameSite=Strict; на HTTPS — Secure.
6. На странице `/library.html` войдите по коду и нажмите **Сохранить в облако** у нужного черновика. Только после явного сохранения этот черновик получает автоматическую облачную синхронизацию в редакторе. На другом устройстве войдите в тот же аккаунт и выберите **Открыть версию из облака**. Загрузка создаёт местную запись, сохраняя ранее открытые черновики.

Перед запуском выполните `npm run account:check`. Команда читает `.env`, проверяет формат адресов, наличие ключей, доступность таблицы облачных черновиков и при наличии публичного ключа — Supabase Auth. Она не выводит ключи и данные пользователей, не изменяет базу и не отправляет письма. Код завершения `0` означает, что эти проверки прошли; `1` — требуется настройка. Если `.env` ещё нет, сначала создайте его по `.env.example`.

Проверка запущенного приложения: `/api/account/session` возвращает `configured` (параметры авторизации заданы), `storageReady` (таблица доступна) и текущего пользователя. Эти проверки не подтверждают доставку email: первый реальный вход необходимо проверить отдельно.

При конфликте версий сервер возвращает 409, оставляя местные правки. Редактор приостанавливает автоматическую отправку, но позволяет продолжить редактирование на устройстве. Устаревшая вкладка библиотеки также не может перезаписать более новую облачную версию. Откройте облачную версию как отдельную местную запись либо создайте копию местного черновика и сохраните её отдельно. Оплата, гости и секрет владельца при создании копии не переносятся. При переносе существующего опубликованного приглашения в аккаунт сервер проверяет исходный токен владельца.

Реальная доставка писем, миграция и вход между устройствами в текущем окружении не проверены. На момент реализации в локальной конфигурации отсутствовали `SUPABASE_ANON_KEY` и `PUBLIC_URL`.

Официальные источники: [вход по email-коду](https://supabase.com/docs/guides/auth/auth-email-passwordless), [Supabase Auth REST](https://github.com/supabase/auth).
